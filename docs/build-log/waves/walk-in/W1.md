# W1 — Walk-in sale on the server

Branch `feature/w1-walk-in`, code commit `0548b98` (based on `3b252c0`).

## What was built

- **Migration** `20261011120000_customer_walk_in`: `customers.is_walk_in` boolean, default false,
  written with `prisma migrate diff`, plus a hand-written partial unique index
  `customers_one_walk_in ... WHERE is_walk_in` (Prisma cannot express it; a future `migrate diff`
  will offer to drop it — delete that line). Applied only to a throwaway container.
- **`common/walk-in.ts`**: `walkInCustomer(tx)` finds the record or makes it with
  `INSERT … ON CONFLICT (is_walk_in) WHERE is_walk_in DO NOTHING`, inside the sale's transaction;
  `assertNotWalkIn`; `PAYMENT_METHODS` (the four the web dialog offers).
- **`POST /sales/orders` with `walkIn: true`**, `payment: { method }` (CASH by default). One
  transaction: walk-in record → `prepareDraft` → `confirmWithin` → `PaymentsService.recordWithin`
  (new: the payment + ledger inflow + `allocateWithin`, which `PaymentsService.create` now also
  uses). Payment dated `businessToday()` (Cairo). Channel forced B2C; currency defaults to EGP.
- **Refusals**: `walkIn` + `customerId`, a non-B2C channel, an unknown method, a non-boolean
  `walkIn`, or `payment` on a non-walk-in sale → `VALIDATION_FAILED`; `confirm: false` →
  `WALK_IN_NOT_DRAFT`; editing/verifying the record, or naming it as `customerId` on an ordinary
  sale → `WALK_IN_RESERVED`; a credit-note return on a walk-in order → `WALK_IN_REFUND_IN_MONEY`.
  All three new codes are in `en.json` and `ar.json`.
- **Hidden / counted**: `GET /customers` (every picker) filters `isWalkIn: false`; the dashboard's
  customer count excludes it; revenue includes its sales (unchanged code). Walk-in returns default
  to CASH.
- **Seeds**: the reference level's "Walk-in Customer" is renamed "Walk-in", verified and flagged;
  the demo level gets one via `walkInCustomer`. Both checked idempotent on a throwaway database.
- **`check-data.sh`**: 16 (walk-in owes money or holds a draft), 16.1 (walk-in can sign in).

## Revert checks (rule 2)

- **One transaction**: `walkInCustomer(tx)` → `walkInCustomer(this.prisma)` made "Not enough
  stock … no walk-in record left" fail (and the race test). Restored, passes.
- **The unique walk-in record**: replacing the `ON CONFLICT DO NOTHING` insert with a plain
  `create` made the race test fail with a unique violation on `is_walk_in`; also dropping the
  index made it fail with two records. Restored, passes.

## Guesses (written into BUSINESS_LOGIC §4, open)

A zero-total walk-in sale takes no payment; a credit refund is refused rather than converted; the
walk-in record cannot be the customer of an ordinary sale; the dashboard customer count leaves it
out; a payment on a non-walk-in sale is refused. The reference seed's B2C example customer is now
the walk-in record, so that level no longer lists a named B2C buyer.

## Noticed, not fixed

- Two concurrent sales (walk-in or not) can compute the same `orderNo`; without an idempotency key
  the loser surfaces as an unexpected error. Pre-existing.
- `PaymentsService.create` still dates an undated payment `new Date()` (UTC day, not Cairo).
- Running the demo seed on top of the reference seed fails on `shop_owner_user_id`. Pre-existing.
