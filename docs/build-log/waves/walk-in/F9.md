# F9 — Three older bugs W1 found

Branch `fix/f9-numbers-dates-seeds`, based on `871c8dd`. No migration.

## What was fixed

1. **Two orders at once could share a number.**
   - *Sale orders*: `order_no` already had a unique index, so the second of two
     concurrent sales failed with P2002 and answered "An unexpected error
     occurred". `SalesService.create` now runs the losing sale again (up to 10
     times). Its transaction has rolled back, so the retry reads the winner's
     number, takes the next, and re-runs every check (stock included). A repeated
     idempotency key still answers with the first order. The format stays
     `ORD-YYYY-NNNNN`. No constraint was added, so production's ORD-2026-00001/00002
     are untouched.
   - *Purchase orders*: `purchase_orders.reference` has **no** unique index, and
     the red run showed six concurrent orders all handed the same PO number with
     nothing objecting. A unique index was not added because production's existing
     references have never been checked for a pair, and a failing migration blocks
     the deploy. Instead `PurchasesService.create` takes
     `lockReferenceSeries(tx, 'PO')` (`common/references.ts`, a transaction-scoped
     `pg_advisory_xact_lock`) before numbering. New `check-data.sh` check **17**
     counts PO references already shared. Run it against production. Zero there
     means a unique index can follow safely.
   - *Payments*: they generate no number (`reference` is typed in, or is the
     idempotency key / walk-in order number), so they don't have this bug.
2. **An undated `POST /payments` was dated by the UTC day.** It is now
   `new Date(receivedOn || businessToday())`, the Cairo day (§7a), as the walk-in
   sale already did.
3. **The demo seed failed on top of the reference seed.** Both levels gave the
   one store login (`shop.owner@example.com`) to their own shop, and
   `shop_owner_user_id` is unique. `giveStoreLogin` now verifies the shop and
   leaves the login with whichever shop already has it. A seed laid over existing
   data adds to it and does not move anything.

## Not fixed

- **The assistant's receipt path** (`assistant/receipt/receipt-writes.ts`) calls
  `writeOrder` in its own transaction without the PO lock. It was out of scope
  for this task, and its spec's fake database has no `$executeRaw`. The fix is
  one line, `await lockReferenceSeries(tx, 'PO')` before `writeOrder`, or
  moving the lock into `writeOrder` once that fake supports it.
- Cycle codes, SKUs, return, plan and order-request references use the same
  read-max-plus-one pattern. Each has a unique index, so a race there is an opaque
  500, not a duplicate. They can take the same retry or lock if it is ever seen.
- The `ORD-`/`PO-` year comes from `new Date().getFullYear()`, which is the server's
  year, not Cairo's. Between 22:00 and midnight UTC on 31 December this gives the
  old year.

Docker was not running at the start. The scratch container `f9_scratch` was
removed and Docker Desktop was quit afterwards. No other container was touched.
