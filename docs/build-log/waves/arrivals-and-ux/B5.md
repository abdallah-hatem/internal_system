# B5 — Refunds for goods lost on the way

Branch `feature/arrivals-b5`, code commit `7ab832d` (based on `866ca7a`).

## What was built

- **Migration `20261010160000_loss_refunds`** (written with `prisma migrate diff`, applied only to a
  throwaway database): `supplier_refunds` gains nullable `shipment_loss_id` → `shipment_losses`
  and `payer_shipping_provider_id` → `providers`, both `ON DELETE RESTRICT`, both indexed. Purely
  additive; existing refunds read as "the order's supplier, against no loss".
- **`POST /shipping/losses/:id/refunds`** `{amount, currency, fxRateToEgp, recordedOn?, payer:
  {type: 'SHIPPING_PROVIDER'|'SUPPLIER', id}, reason?}`, `RolesGuard` + CORE_PARTNER, DTO
  `CreateLossRefundDto` (shape only). Lives in `ShippingController`, delegates to
  `PurchasesService.recordLossRefund` (ShippingModule imports PurchasesModule).
- **One refund writer.** `purchases.service.ts` `bookRefund(tx, po, …)` holds the order-level cap,
  the `SupplierRefund` row and the ledger inflow; `recordRefund` (plain) and `recordLossRefund`
  both call it inside a transaction holding `lockCycle`. So the order cap counts loss refunds, and
  there is one ledger write. `checkRefund` (both paths): amount > 0 and whole cents, rate > 0,
  currency given (`VALIDATION_FAILED` {fields}), `DATE_IN_FUTURE` on a Cairo day after today.
  `recordedOn` is stored as the Cairo day (today in Cairo when left out).
- **Loss refund rules**: unknown/non-uuid loss → 404 `shipmentLoss`; payer SUPPLIER must be the
  loss's order's supplier, SHIPPING_PROVIDER the loss's leg's `providerId`, else 404
  `supplier`/`provider`; Σ `refundEgp` on the loss + this one > `costEgp` → `REFUND_EXCEEDS_LOSS`
  {cost, refunded, asked, product}. Any cycle status.
- **`refundEgp`** (`common/loss-refunds.ts`) = amount × rate, 2 dp half up — the ledger's figure.
  Both caps, the read and check-data add refunds up the same way.
- **Ledger**: type `SUPPLIER_REFUND` (the ledger page already labels it), category `loss_refund`,
  INFLOW, the cycle's id, `relatedType SUPPLIER_REFUND`.
- **Profit**: `loss_refund` added to `COST_RECOVERY_CATEGORIES` with an `isCostRecovery` helper.
  Settlement already read the list. **Found on the way and fixed:** analytics cycle profitability
  tested `category === 'supplier_refund'` by name (would have ignored loss refunds), and the
  dashboard's net profit ignored every recovery, so a supplier refund raised a cycle's profit but
  not the business's. Both now read the one list; the dashboard adds recoveries to `netProfit` and
  reports them as `totalRecoveredEgp` (`totalExpenses` stays gross).
- **Take-back**: `DELETE /shipping/losses/:id` → `LOSS_REFUNDED` {refunds} when any refund names
  the loss (counted under the cycle lock, after the frozen-cycle check). The FK refuses it too.
- **Read**: `GET /cycles/:id/shipment` — each `legs[].losses[]`, and a new flat top-level
  `losses[]`, is `{ id, legId, purchaseOrderItemId, qty, unitCostEgp, costEgp, reason, createdAt,
  refundedEgp, unrecoveredEgp, refunds:[{id, amountEgp, currency, amount, recordedOn, payerType,
  payerName}] }` (money as fixed-point strings, `qty` a number). `loadShipment` now selects
  `unitCostEgp`.
- **check-data 12.8** "refunds on a loss exceed its cost". (Its comment notes that bash 3.2 reads
  an apostrophe in that heredoc as a quote — the first draft broke the script.)
- **Providers**: deleting a provider that paid a loss refund → `PROVIDER_IN_USE` (else a 500 on
  the FK once the leg moved to another company).
- **Codes**: `REFUND_EXCEEDS_LOSS`, `LOSS_REFUNDED` in `errors` of en.json and ar.json.

## For F1a

The dialog reads `losses[]` (top level or per leg) from `GET /cycles/:id/shipment`; posts to
`/shipping/losses/:id/refunds`; the payer choices are the leg's `providerId` (from the leg) and
the order's supplier. A leg with no `providerId` can only be refunded by the supplier.

## Guesses (open until confirmed)

1. **A refund cannot be undone.** §6 says a refunded loss that turns up is fixed by undoing the
   refund first, but no path exists: the ledger refuses to reverse a flow-raised row on its own,
   and there is no refund reversal. Until one is built, `LOSS_REFUNDED` is permanent.
2. **`recordedOn` is optional** (today in Cairo), as for plain refunds; the spec lists it without
   saying.
3. **Amount ≤ 0 → `VALIDATION_FAILED` {fields: amount}**, not `QTY_NOT_POSITIVE` (it is not a
   quantity; `AMOUNT_NOT_POSITIVE` says "a payment").
4. **The dashboard shows recoveries apart** (`totalRecoveredEgp`, added to `netProfit`) rather
   than netting them into `totalExpenses`. Settlement nets them; the profit agrees either way.
5. **Both caps sum per-refund rounded EGP** (`refundEgp`), where the order cap used to sum
   unrounded amount × rate. They differ by under a piastre per refund.
6. **A loss refund is ledger type `SUPPLIER_REFUND`** even when the shipping company paid; the
   category (`loss_refund`) and the refund row tell them apart.
7. **A leg with only a free-text provider (no `providerId`)** cannot name the company as payer.
8. **Payer checks are against the leg and order as they are now**, not when the loss was marked.
