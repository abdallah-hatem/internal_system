# U1: The sale form and list

Branch `feature/ux-u1-sales`. API commit `c9415f8`, web commit `6688fa2`, plus the e2e spec and
this log. Business rule: BUSINESS_LOGIC §4, DECIDED 2026-10-10 (created and confirmed in one
step).

## API

- `POST /sales/orders` takes `confirm?: boolean`. Only `true` confirms; anything else saves a
  draft, as before. Roles are unchanged (`CORE_PARTNER`, `ADMIN_SUPPORT`, class-level guard).
- The confirm logic moved into `confirmWithin(tx, …)`. `POST /:id/confirm` and the
  create-and-confirm path both call it. On the one-step path the validation, the draft insert
  and the confirmation all run in **one** `$transaction`, so any refusal (stock, discount,
  unknown customer or product, the FIFO allocation running short) leaves no draft. Audit rows
  are written after the commit, as before (`connection_limit: 1`).
- **Idempotency.** SaleOrder has no column for a key, and adding one was outside this task's
  files (the schema belongs to B1). So `Idempotency-Key` (the header payments already uses) is
  remembered **in-process** for 10 minutes, per user. A second request with the key while the
  first is in flight, or after it succeeded, gets the first one's answer. A refused attempt is
  forgotten, so fixing the lines and retrying works. This covers a double-click on one API
  instance. Two serverless instances would not share the map. The form also disables its
  buttons and guards with a synchronous ref. A durable key needs a column: **open**, not decided.
- **One formula.** `common/sale-totals.ts` holds the line and order total in integer
  arithmetic: gross = qty × price rounded to the cent, minus the discount. The service stores
  these numbers. Before, it used `unitPrice * quantity` in floating point.
  `apps/web/src/lib/sale-totals.ts` is a copy, because Next cannot import across apps. A
  Vitest parity test runs both over a grid of 891 lines and fails if they ever differ.

## Web

- `components/sales/SaleOrderForm.tsx` (new) is the create form, moved out of the page so it
  can be component-tested. It starts with one empty row. Below 768px each line is a card: the
  product row, then a qty / price / discount grid with room for full values. Each line shows
  its total and the form shows the order total. **Save as draft** comes first in the DOM, so
  Enter in a field never confirms a sale. **Create & confirm** is the primary button. A
  refusal keeps the dialog open with its lines and shows `useApiError()` text in a
  `role=alert`. A typed price is tracked per line (`priceTyped`) and never replaced by a list
  price, whether the product or the channel changes. The old rule ("untouched = equals the old
  list price") misread a typed price that happened to match.
- `sales/page.tsx`: rows open on a click anywhere. The order number is a real button. Phone
  cards are `role=button` and open on Enter or Space. A draft shows "— (not confirmed)" for
  outstanding, in the list and the detail. Status goes through `useCodeLabel`. The first chip
  reads "All" and has `aria-pressed`. `EmptyState` shows when no orders exist. The dates use
  `useDateFormat`. Success toasts are translated. The detail's line total is the stored
  `lineTotal`, not recomputed. The modal is tighter on a phone and its close button is 44px.
- Keys added under `sales` only (en + ar). No new error codes.

## Tests

- API jest: `sales.create-confirm.spec.ts` (20) with an in-memory Prisma whose `$transaction`
  really rolls back, and `common/sale-totals.spec.ts` (7). The full suite is 443 tests, all
  passing.
- Web Vitest: `SaleOrderForm.test.tsx` (11) and `sale-totals.test.ts` (3). The full suite is
  34 tests, all passing.
- E2E (written, **not run**): `tests/76-sale-create-confirm.spec.ts`, TC-CC-01…13. Tests 30
  and 33 no longer click "Add item" after opening the sale form, because it starts with one
  row now.
- **Revert checks (rule 2).** Each change below was reverted, the test run, and the change
  restored:
  - Removing the transaction fails "no draft left behind when the confirm step itself
    refuses".
  - Removing the key map fails "Double-click Create & confirm → one order".
  - A float `qty*price` total in the form fails the per-line rounding test.
  - Dropping the form's ref guard fails "a double-click sends one request".
  - Ignoring `priceTyped` fails "a typed price is not overwritten".
  - The NOT_ENOUGH_STOCK no-draft test passes with or without the transaction, because that
    check runs before the insert. The FIFO-short case is the one only the transaction can
    clean up.
