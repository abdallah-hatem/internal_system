# B1 — Deliveries and losses in the data model, and the one position function

Branch `feature/arrivals-b1`, code commit `09ebb8e` (based on `b571e63`).

## What was built

- **Schema.** New `ShipmentDelivery` (leg, `arrivedOn` as a date, note, createdBy),
  `ShipmentDeliveryLine` (delivery, order line, qty; unique per delivery and order line) and
  `ShipmentLoss` (leg, order line, qty, unitCostEgp, costEgp, reason). `InventoryBatch` loses
  `sourcePoItemId @unique` (now just indexed), and gains `sourceDeliveryLineId` (indexed, not
  unique) and `arrivedOn`. `PurchaseOrderItem.inventoryBatch?` became `inventoryBatches[]`. Leg
  `status` is still a string, and its doc comment now lists `PARTLY_ARRIVED`.
- **Migration** `20261010120000_shipment_deliveries`. It only adds things: created with
  `prisma migrate diff`, plus CHECKs that delivered and lost quantities are positive and loss
  costs are not negative. It was not applied to any database.
- **`common/shipment-position.ts`.** `shipmentPosition(input)` is pure, sums in whole
  thousandths, and exports `LEG_STATUSES`.
- **Backfill.** `common/shipment-backfill.ts` (`planShipmentBackfill`, pure) and
  `prisma/backfill-shipment-deliveries.ts`, run as `npm run db:backfill:deliveries` or
  `scripts/ship-prod.sh backfill`. Each cycle is written in one transaction under an advisory
  lock.
- **`GET /cycles/:id/shipment`.** `RolesGuard` + `@Roles('CORE_PARTNER')`. Returns
  `notFound('cycle')` for an unknown id, and for an id that is not a uuid (without querying).
- **Kept compiling, same behaviour.** In `inventory.service.ts`, the two duplicate-batch checks
  changed from `findUnique({ where: { sourcePoItemId } })` to `findFirst`. In the
  assistant's `cycle.spec.ts`, the mock's `findUnique` became `findFirst`, and its fake
  unique-index rejection on `create` was removed (that index no longer exists).

## Tests

- jest: 24 suites, 452 tests, all passing. New: `shipment-position.spec.ts` 17,
  `shipment-backfill.spec.ts` 14, `cycles-shipment.spec.ts` 5.
- e2e: `apps/web/tests/73-shipment-position.spec.ts`, 7 cases. Written, **not run** (the main
  thread runs e2e).
- Revert checks:
  - Removing `@Roles('CORE_PARTNER')` from `getShipment` makes "as an investor or shop →
    refused with a code" fail.
  - Removing the loop that carries a leg's delivered quantity to the next leg's entered makes
    "two legs: leg 1 delivered 30 of 40 → leg 2 entered 30" and "legs given out of order" fail.
  - Setting `waiting` to 0 makes 4 tests fail.
  - All tests passed again after each revert was undone.

## What the plan got wrong, and the guesses (open until confirmed)

1. **The backfill is not inside the migration.** The task said "one migration, additive +
   backfill". Migration SQL cannot be unit-tested here without applying it to a database,
   which was not allowed. So the backfill is a tested TypeScript planner plus a script, and
   **production needs `scripts/ship-prod.sh backfill` straight after `migrate`**. Until it
   runs, legacy batches have no delivery line. `reset-db.sh` does not need it: a fresh
   database has nothing to backfill.
2. **A loss on the last leg comes out of "on the way" first, then out of "waiting".** The spec
   is silent on this. Per delivery line, `received` is reported raw, and a loss is not
   assigned to a delivery. B3's receipt guard must also cap at the line-level `waiting`, not
   only at the delivery line's qty − received.
3. **The backfill gives an undated earlier leg the batch day too.** On a China cycle with
   batches but neither leg dated, the spec names only the last leg. Without this, leg 2 would
   have delivered more than entered it.
4. **A cycle with batches but no legs is left as it is.** There is no leg to hang a delivery
   on. Its batches still count as received, so it is accounted only if they total what was
   ordered.
5. **"Short" means the line's batches total less than ordered,** not the `receivedQty`
   column, which is the same thing for legacy data. A line with no batch is waiting, not
   short.
6. **A leg where every unit was marked lost reads ARRIVED with `arrivedOn` null.** A leg with
   nothing entered (nothing ordered) reads IN_TRANSIT or PENDING, never ARRIVED.
7. **Dropping the unique index removes the database's backstop against two concurrent
   receipts of one line.** Only the in-transaction `findFirst` check remains until B3 replaces
   verify.
8. Not covered by B1: "check-data clean" and "check-data does not flag historical rows"
   (check-data is B2's). The `PARTLY_ARRIVED` translation for the web (UI tasks).
