# L1 — List pages hid records

Branch `fix/l1-lists-hide-records`, from `b3cc1d9`. This is the follow-up the e2e fixes left open
(`e2e-fixes.md`, "Still open").

## The bug

The office list pages search and page on the client, over whatever they fetched. Most of them
called `api.get('/x')` with no limit and got the API's default page: the newest 20. From the
21st-newest record on, a purchase order, product, cycle, sale, payment, ledger entry or audit
entry was not on its page, and searching for its reference found nothing. Suppliers, customers,
shipments and the settlement cycle picker asked for 200. That only moved the wall. A customer's
page fetched 100 orders and 100 payments, so the "paid" tile was also wrong past 100.

The API had a second problem that blocked the obvious fix. Following `nextCursor` showed rows
twice. Prisma's cursor is inclusive, and only payment plans and returns passed `skip: 1`. Every
list was also ordered by `createdAt` alone. Rows written in one transaction share `createdAt`,
because Postgres `now()` is the time the transaction started. So a page boundary inside a tie
could skip one row and repeat another.

## Approach

All pages share one helper: `apps/web/src/lib/list-all.ts`.

- `fetchAll(path, params)` walks the cursor pages, 200 rows at a time (the API's maximum). It
  stops at `LIST_CAP` = 2,000 rows. It returns `{ items, capped }`. An endpoint that does not page
  is asked once. If the cursor stops moving, the walk ends.
- `useAllRecords(key, path, params, { enabled })` wraps it in `useQuery`. Every list that reads a
  paged endpoint now uses it. One query key therefore means one fetch everywhere. Before this,
  `['products']` held 20 rows or 200, depending on which page filled the cache first.
- `<ListCapNotice>` (`components/ui/list-cap-notice.tsx`, `common.listCapped` in en/ar) shows
  "Showing the first N only…" when the list was cut at the cap. A cut list never looks complete.

I chose fetch-everything over server-side search. The pages already filter, count and paginate on
the client (status chips with counts, select filters, the customer balance sort). Moving each one
to server search would mean ten different rewrites. 2,000 rows is far beyond any list in this
business today. If a list does reach the cap, the notice says so.

## API order, per endpoint

Every cursor list now builds its page with `cursorPage(cursor, limit)` from
`common/dto/pagination.dto.ts` (`take: limit + 1`, `cursor`, `skip: 1`). It refuses a non-uuid
cursor with `VALIDATION_FAILED` (400) instead of failing with a 500. Each order now ends on `id`:

- newest first, `[createdAt desc, id desc]`: cycles, customers, payments, purchases, ledger,
  products, sales orders, settlements, users, payment plans, returns, notifications.
- audit logs: `[occurredAt desc, id desc]`.
- suppliers, a catalogue sorted by name: `[name asc, id asc]`.
- shipping legs: newest cycle first, then `cycleId`, `sequence`, `id`.

Products stayed newest first, not by name. The products page shows them in that order, and
changing it was not part of this task.

## Tests

- **API jest**, `src/common/dto/cursor-paging.spec.ts` (12): a fake `findMany` with Prisma's
  inclusive cursor, which shuffles tied rows on every call the way Postgres may. Walking the pages
  of purchases, products, suppliers and cycles must return 45 rows, each exactly once, across a
  20-row `createdAt` tie. Repeating the same request must return the same page. `cursorPage` is
  checked for a missing cursor, a valid one, and an injection-shaped one. With the services
  reverted, 8 of the 12 fail. With the fix, all 12 pass.
- **Web Vitest**, `src/lib/list-all.test.tsx` (14), covering:
  - 450 rows walked in order
  - the page size is 200
  - the filter is kept on every page
  - a list past the cap is marked capped; one exactly at the cap is not
  - an empty list, an endpoint that does not page, a bare-array body, and a stuck cursor
  - the hook returns the 25th row
  - the empty array stays stable while loading is disabled
  - the notice in English and Arabic, and nothing when the list is complete

  With the helper changed back to a single default-size fetch, 6 fail.
- **Playwright**, `tests/91-lists-show-everything.spec.ts` (8, not run here). Each test makes the
  record it will search for first, then enough newer ones to push it off the old page: 25 for
  products, purchases, cycles, sales, payments and ledger, and 201 for suppliers (sorted by name)
  and customers. It signs in, clicks through the menu, searches, and expects the row to show. Every
  record is built the way the business builds it: payments need owed, confirmed orders on received
  stock. Against the old pages, each test fails because the row was never fetched.
- `inventory-receive.test.tsx`: the mock matched `/cycles?limit=200` in the URL. The helper sends
  the limit as a param, so the mock now also matches `/cycles`.

Results: API jest 818 passed, 9 skipped. Lint and typecheck clean. Web Vitest 228/228, node 84/84.
Lint has 0 errors (45 warnings, the same count as before). Stale suppressions were pruned.
Typecheck clean.

## Not covered by Playwright

Shipments (200 legs), payment plans (100), a customer's page (100 orders) and audit logs. Reaching
their old walls through real records costs hundreds of cycles or orders. The shared helper they
now use is what the Vitest cases cover.
