# U5 — Arabic everywhere

Branch `feature/u5-arabic`, from `5bb65b0`. Spec A #10 and #12.

Not touched (other tasks in the wave): the dashboard page and `nav-model` (R1),
`components/shipment/ShipmentPanel.tsx` and `RecordRefundDialog.tsx` (B5b).

## 1. Codes on screen

Every status, role, method, basis, type and channel code now goes through
`useCodeLabel`. New kinds, each a sub-object of `codes` in both locale files:
`poStatus`, `settlementStatus`, `originType`, `verificationStatus`,
`movementType`, `referenceType` (inventory movements and ledger "related to"),
`auditAction`, `entityType`. A cycle participant's type uses `role` (same
values).

Fixed: purchases (list, cards, detail), customers (orders in the detail),
cycle details (participant type, batch verification), products/[id] and
inventory (movement and reference types, price-history channel), audit logs
(action chip, entity, filter options, modal title), settlements (status chip),
analytics (origin · status), ledger (related record), settings (role field),
partners CSV (role, cycle status), the header's role line (was
`replace(/_/g, ' ')`), the sale form (customer-type hint, channel), the cycle
pickers' hints on purchases, shipping legs and settlements, the payment-plan
customer hint, and the shipping-cost fields — which were wholly English,
basis options included, and are now translated (`shippingCost.*`), as is the
currency/rate control's helper text.

Guard: `apps/web/unit/no-raw-codes.test.mjs` (node:test, in `test:unit`, the
same shape as U4c's controller-reading test). It walks every TSX file under
`app/[locale]` and `components` and fails on a code as a JSX child, handed to a
display prop or an option `label`/`hint`, pasted into a template sentence, or
prettified with `replace(/_/g, ' ')`. Pointed at the tree before this task
(`U5_SCAN_ROOT`), it reports **27**; now **0**. It found the ledger's related
type, which the review had not.

## 2. Dates

14 files still imported the plain `formatDate`/`timeAgo` (English whatever the
reader chose): customers, cycle details, audit logs, shipments, ledger,
purchases, products/[id], import and order requests, inventory, payment plans,
notifications, the bell, assistant connections. All now use `useDateFormat()`.
No `toLocaleDateString` or `en-US` remains outside `lib/dates.ts`, the date
picker's own locale map and the money input's digit grouping (deliberately
Latin).

## 3. Toasts

15 success toasts and 19 failure fallbacks were English literals (customers,
products, product prices, purchases and refunds, ledger, shipping legs,
settlements, settings, suppliers, providers, categories, the sale return, the
equal split). Each is a key in its page's namespace; the English wording is
unchanged, so existing Playwright assertions still read the same text.

## 4. Forms

`components/ui/validated-form.tsx`: a drop-in `<form>` that sets `noValidate`
and keeps the rules. On submit it asks the constraint API (`checkValidity`
still works on a `noValidate` form) which fields fail; if any do it stops,
focuses the first, marks each `aria-invalid` (styled in `globals.css`), and
shows one translated line naming them — "يرجى ملء الحقول المطلوبة: الاسم".
`checkValidity` fires each field's `invalid` event, so the shared `Select` and
`DatePicker` show their own "Required" as before. Other rules (`min`, `type`)
get "يرجى مراجعة هذه الحقول: …".

29 forms moved to it (every page form, the wizard's three steps, quick-create,
login). The three already `noValidate` (sale form, payment dialog, shipment
dialogs) validate in their own handlers; the sale form posted an empty
customer or product to the API, so it now checks both itself with the same
message.

Two unit tests changed because they submitted forms a person could not:
the sale-form tests now start with a customer chosen, and the wizard's
"saving the legs forgets the unsaved copy" picks a provider and a rate before
saving (it used `fireEvent.submit`, which bypassed the browser's check).

## 6. Notifications

**Server.** `Notification` gains nullable `code` and `params` (JSON).
Migration `20261010180000_notification_code_params`, additive, written with
`prisma migrate diff`, **not applied anywhere**. Every service names what
happened with a code; `common/notification-messages.ts` is the one catalogue
(16 codes, en and ar), and `NotificationsService` derives the English `title`
from it, so no service writes the sentence and the two cannot disagree. The
title stays as what logs record and what an old client shows.

**Web.** `useNotificationText()` in `lib/notifications.ts` renders
`notifications.<code>` with the params; a param that is itself a code
(`toStatus`) is translated too. A notification with no code — every row
written before this — or with a code the build does not know shows its stored
`title`. The bell and the notifications page use it.

**Push — decided.** A push is worded on the server while no app is open, so
the server must pick a language. `pushLocaleFor(reader)`:

1. the reader's stored locale, if there is one — **nothing stores one today**
   (no column on `User` or on the push subscription); the parameter is there so
   adding one is a one-line change;
2. otherwise the default of the app that person reads: a shop
   (`SHOP_OWNER_PORTAL`) reads the storefront, which opens in Arabic for
   everyone (BUSINESS_LOGIC §13) → **Arabic**; the office reads the internal
   system, default English → **English**.

Open: an office partner who works in Arabic gets English pushes. Storing the
locale with the push subscription (the page knows it at subscribe time) would
fix that; not done here.

The storefront does not list notifications yet; `/portal/notifications` now
returns `code` and `params` for when it does.
