# B4 — The assistant learns deliveries

Branch `feature/arrivals-b4`, code commit `2c346ff` (based on `866ca7a`).

## What was built

All in `apps/api/src/modules/assistant/**`; no service outside it changed.

- **`record_delivery`** `{legId, arrivedOn, lines:[{purchaseOrderItemId, qty}], note?}` — a
  `writeTool`. `DeliveriesService` has no `plan…` method, and adding one was outside this task's
  files (B5 is editing that service in the same wave), so the preview **is the write, rolled
  back**: `dry-run.ts` hands a fresh `DeliveriesService` a stand-in for Prisma whose
  `$transaction` runs the service's callback — lock, every check, the insert, the audit row — then
  reads the shipment inside that transaction and throws, so Postgres rolls it all back. The
  throw leaves the service before its post-commit notification. No rule is written twice. The
  preview shows, per product, what was on the way, what arrives and what will still be on the
  way, and the leg's status afterwards. It **binds** `[line, qty, onTheWayAfter]`: a delivery
  recorded by someone else in between → `PREVIEW_CHANGED` (still fits) or the service's
  `DELIVERY_EXCEEDS_IN_TRANSIT` (no longer fits); the token is not spent and nothing is written.
- **`verify_stock`** now takes `{deliveryId, items:[{deliveryLineId, receivedQty,
  landedUnitCostEgp?}]}`; the cycle is the delivery's (a non-uuid or unknown id →
  `NOT_FOUND shipmentDelivery`). Preview from B3's `planVerification`: the per-ordered-unit
  landed cost, the line cost, the total, and whether this receipt moves the cycle to SELLING.
  Binds `[deliveryLineId, landedUnitCostEgp, lineCostEgp]` + total, so a corrected leg cost (or
  a loss that moves the final-event residual) → `PREVIEW_CHANGED`. Works on a later delivery
  while SELLING. The description drops "verified once" / "VERIFICATION": it explains deliveries,
  what is waiting to be received, short counts, and the first receipt walking to SELLING.
- **`add_shipping_leg`**: an arrival date's preview lists the units it will deliver — read from
  `shipmentPosition` with the new leg added (the reading `createLeg` delivers by) — and the leg's
  status from that. Binds that list, so leg 1 delivering more in between → `PREVIEW_CHANGED`.
  The description says to leave the date out and use `record_delivery` when goods came in pieces.
- **`get_cycle`** adds `shipment` from `CyclesService.getShipment` (the office panel's method):
  totals, per product, per leg status / entered / delivered / lost / on the way / received /
  waiting, and each delivery with its line ids. Order lines and legs now carry their `id`, which
  the delivery tools take. **`get_stock`**: Arrived is the batch's own delivery date.
- **`instructions.ts`**: a "Deliveries" paragraph — record each delivery as it comes, receive it
  with `verify_stock`, losses and refunds belong to the office app.
- **No loss or refund tool.** No new error codes.

## Guesses (open until confirmed)

1. **`verify_stock` takes no `cycleId`.** The delivery names its cycle; asking for both only adds
   a way to disagree.
2. **The delivery preview is a rolled-back write**, not a plan method on `DeliveriesService`. It
   holds the cycle lock for the preview's few queries. A `planDelivery` in the service would be
   the tidier home once B5 has landed.
3. **`add_shipping_leg` binds its delivered units always** (an empty list without an arrival), so
   every confirm re-previews it.
4. **`verify_stock` binds the line cost too**, not only the unit cost: a loss recorded in between
   can move the final event's residual.
5. **Per delivery line, `received` is shown on the last leg only**; earlier legs' lines are never
   received into stock.
