# U2: Payments against a chosen order, one payment form

Branch `feature/ux-u2-payments`. API commit `2bd1323`, web commit `c71ef6d`, plus this log.
Business rule: BUSINESS_LOGIC §7, DECIDED 2026-10-10 (a payment can be put on a chosen order).
Follow-ups from the U1 merge: the sale idempotency key is stored, and a negative discount is
refused (decisions log, last two entries).

## API

- `POST /payments` takes an optional `orderId`. The payment, its ledger inflow and the
  allocation are written in **one** `$transaction`. The allocation goes through
  `allocateWithin(tx, …)`, which is now the only allocation code. `POST /payments/:id/allocations`
  calls it too. Audit rows are written after the commit.
- Checks on the chosen-order path, in order: a repeated `Idempotency-Key` returns its payment
  before anything else runs. Then amount > 0 (`AMOUNT_NOT_POSITIVE`), no future date
  (`DATE_IN_FUTURE`, Cairo), the customer exists and is verified. Then the order: someone
  else's order or an unknown id → 404 `NOT_FOUND` (`saleOrder`). A draft →
  `ORDER_NOT_CONFIRMED`. Cancelled, returned, paid, or outstanding 0 → `ORDER_OWES_NOTHING`.
  More than it owes → `PAYMENT_EXCEEDS_ORDER` (`owed`, `asked`). The cap is
  `order.outstanding`, which a credit note already lowers (§5), so it is net of returns. The
  shop-wide `PAYMENT_EXCEEDS_OWED` check is skipped on this path because the order's own cap is
  tighter and names the order.
- Without `orderId` nothing changes. The payment is recorded unallocated, and the caller
  applies it oldest first.
- **Also changed on the Allocate path:** allocating to a draft is now refused
  (`ORDER_NOT_CONFIRMED`), and to a closed or zero order too (`ORDER_OWES_NOTHING`). §7a already
  said a draft cannot be paid against, but nothing enforced it there. Someone else's order is
  still `ORDER_OTHER_CUSTOMER` on that path.
- A chosen-order payment stays `RECORDED` with the customer's id, so the payment plan's
  `paidSince` counts it. A test runs the real `PaymentPlansService` to prove it.
- Roles are unchanged: `CORE_PARTNER` and `ADMIN_SUPPORT` at the class level.
- **Sale idempotency.** `SaleOrder.idempotencyKey` is nullable and unique with `createdBy`
  (migration `20261010140000_sale_order_idempotency_key`, additive; written with
  `prisma migrate diff`, **not applied** to the shared DB). `create` first looks up
  (createdBy, key). If the insert loses a race, the unique violation (`isUniqueViolation`) is
  caught and the winner's order is returned. The in-memory map is gone. Payments do it the same
  way: the header is `Idempotency-Key`, a lookup runs before the write, and `{ data: existing }`
  comes back. Theirs lives in `reference` and has no index, so the sale version is the stricter
  of the two.
- **`DISCOUNT_NEGATIVE`** is checked in `prepareDraft`, which every create path runs through:
  draft, create & confirm, and the storefront's approval. Sale orders have no edit path.

## Web

- `components/payments/RecordPaymentDialog.tsx` (new) is the only form that records a payment.
  It portals to `body` (`z-[60]`) the way quick-create does, so it sits above the sales page's
  inline order modal.
  - From an order, it shows "ORD-… owes", defaults the amount to the order's outstanding, and
    posts with `orderId`.
  - From a customer, or from the Payments page with its picker, it shows what the shop owes in
    total and applies the money oldest first. If an allocation fails after the payment is
    recorded, it closes with a warning instead of staying open to be sent twice.
  - The date is Cairo's today, with `disableFuture`. Methods are Cash, Bank transfer and
    Mobile wallet, labelled through `useCodeLabel('paymentMethod')`.
  - A refusal shows in a `role=alert` through `useApiError()`, and every value stays as typed.
    Zero, and more than the order owes, are caught before sending, in the server's wording.
  - Double submit is guarded by a ref and the disabled button.
- `customers/[id]/page.tsx`: the old inline modal and its record-then-allocate mutation are
  gone; it opens the dialog. Drafts show "— (not confirmed)". Status, method and type use
  `useCodeLabel`, and dates use `useDateFormat`. `EmptyState` appears for no orders and no
  payments.
- `payments/page.tsx`: the create modal is replaced by the dialog. Allocate stays for older,
  unallocated payments, and its order list now leaves out drafts. Methods and statuses use
  `useCodeLabel`, and the old `METHOD_KEYS`/`STATUS_KEYS` maps are removed. Toasts are
  translated. `EmptyState` shows when there are no payments, but not when a search finds
  nothing.
- `sales/page.tsx` (**U1's page**): only a "Record payment" button in the order detail, shown
  when the order is confirmed and still owes (`canTakePayment`), plus the dialog. The payment
  history line's method now reads through `codeLabel`.
- Keys added under `payments`, `customers` and `errors` (5 codes), in en and ar.

## Guesses (written down, not decided)

- The order path answers someone else's order with 404, not `ORDER_OTHER_CUSTOMER`. The plan
  said 404, and an order picked from a shop's own list is not one it can see. The Allocate path
  keeps its 400.
- `CHEQUE` was offered on the customer page only and has no `codes.paymentMethod` label, so the
  shared list does not offer it. Old cheque payments show the raw code until a label is added.
- The Payments page's currency picker (EGP/USD/AED) is gone. A payment takes the order's
  currency, or EGP, because the caps compare amounts with no conversion.
- Oldest-first still runs from the client, one request per order, as before. Doing it on the
  server in one transaction is the next step if a half-applied payment is ever seen.
- The dialog sends no `Idempotency-Key` for payments, because the key would be stored in
  `reference` and show in every list. The ref guard covers double clicks. A retry after a
  dropped connection is not covered, the same as before.
